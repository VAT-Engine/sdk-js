# JS-02 Node.js package foundation

**Status:** Proposed for approval · 2026-11-28

**Inputs:** [Shared requirements](../../contract/REQUIREMENTS.md), [approved CORE pin](../../contract/manifest.json), [operation catalog](../../contract/operations.json), and [synthetic conformance corpus](../../contract/fixtures/README.md).

## Runtime, modules and compiler

- Support Node `^22.13.0 || ^24.0.0 || ^26.0.0`. These are the maintained LTS lines on the review date. Recommend the newest security patch in each line and review support at each LTS transition. Node 22 reaches end of life on 2027-04-30. Qualify new major lines through consumer tests before advertising support. [Node releases](https://nodejs.org/en/about/previous-releases) · [Node schedule](https://github.com/nodejs/Release/blob/main/schedule.json)
- Publish one server-side ESM build with named exports and a synchronous entry graph. Standard `require()` on the supported Node versions loads the same module namespace and export identities. Use `"type": "module"` and one root export with `"types"` first and `"default"` pointing to the built JS. This avoids a second build with potentially distinct class identities. Top-level await anywhere in the entry graph would break synchronous `require()`, so test the packed artifact through both loaders. Legacy Node and tools that expect physical CommonJS files would gain compatibility from a separate build. Support for those environments and browser bundlers is outside this proposal. [Node require(esm)](https://nodejs.org/docs/latest-v22.x/api/modules.html#loading-ecmascript-modules-using-require) · [Node package exports](https://nodejs.org/api/packages.html#conditional-exports)
- Use `tsc` 5.9.3 as the compiler and build tool. Emit ES2022 and declarations using `NodeNext`, explicit `.js` relative specifiers, `strict`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess` and `verbatimModuleSyntax`. TS 5.9 satisfies the generator's `^5.x` peer dependency and the lint stack. Test TypeScript ESM and CommonJS consumers in `NodeNext`. TypeScript 5.8 introduced the matching `require(esm)` behavior in that mode. A bundler could produce additional targets and offer bundler-specific optimizations. The single Node target has no such build requirement. [TypeScript NodeNext behavior](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-8.html#support-for-require-of-ecmascript-modules-in---module-nodenext)

## Dependencies and contract generation

- Use npm 11.20.0 for development and CI, commit `package-lock.json` and install with `npm ci`. Pin the initial dev tools to the tested versions, review lockfile changes and check the dependency tree before release. npm comes with Node distributions and needs one lockfile. npm 12.2.3 has a higher Node floor than this proposal. Using pnpm would add tool provisioning and lockfile policy without a workspace requirement. Target zero runtime dependencies. [npm ci](https://docs.npmjs.com/cli/v11/commands/npm-ci)
- Use `openapi-typescript` 7.13.0 as a dev-only generator from the verified local OpenAPI. Use its method/path-indexed output, including operations without IDs. Add a deterministic transform for explicit OpenAPI `integer/int64` and retain nullable unions and optional properties. Keep generated paths and transport types internal. Derive public input and output types from the generated models and reviewed operation semantics. A generator that emits a client would also make transport choices and increase the amount of code to review. [openapi-typescript 7.13.0 Node API](https://github.com/openapi-ts/openapi-typescript/blob/openapi-typescript%407.13.0/docs/node.md)
- Use the same pinned schema to derive integer conversion metadata. Key it by operation, status and media as applicable. Cover local references, arrays and composed schemas before applying it to all operations. Review unformatted integers and the backend contract meaning before selecting a representation for them. CI should regenerate and compare checked-in artifacts, verify method/path parity with JS-01, and fail on unsupported or ambiguous precision mappings. Schema generation supplies static types and conversion metadata. It does not establish backend authorization or validate an entire response at runtime.

## Exact JSON and public integers

- Propose `bigint` for declared numeric int64 outputs, and `bigint | number` for declared int64 inputs. The number convenience requires `Number.isSafeInteger` before conversion, and every input must fit the signed 64-bit range. JavaScript can reject an already rounded unsafe number but cannot recover what the caller intended. Values beyond the safe range must be supplied as `bigint`. Reject fractional, non-finite, unsafe and out-of-range inputs locally. Enforce field-specific constraints such as positive supply revisions independently of the representation.
- Parse structured JSON with `JSON.parse` and the reviver's `context.source` for numeric tokens. Convert validated int64 lexemes directly to `bigint`. Emit int64 values as unquoted decimal digits through a scoped `JSON.stringify` replacer and `JSON.rawJSON`. Keep conversion field- and operation-specific. Binary64 fields such as the ECB rate remain numbers, decimal and minor-unit strings stay strings, and omitted fields, explicit `null` and `false` retain their meaning. Supply input `event_version` is an exact integer, while the receipt uses a string. Classify unknown additive properties as data, preserve their precision, and test handling separately from documented fields. For raw JSON attachments, use the documented response media and attachment mode to preserve bytes and digests. [ECMAScript JSON source-text access](https://tc39.es/proposal-json-parse-with-source/)
- Native support avoids a parser dependency and ties exact-number support to the Node baseline. A library such as `lossless-json` could support more environments but would add package maintenance and custom number handling. Using strings for all public int64s would simplify generic JSON consumers and move parsing and validation to the integration. With `bigint`, consumer code must explicitly convert when serializing SDK objects into its own ordinary JSON or crossing systems that lack bigint support. A uniform bigint output avoids the need for callers to branch by magnitude.
- TS 5.9.3's standard library declarations lack the native JSON signatures used here. Keep a minimal typed adapter private and check both features before precision-sensitive use. Unsupported environments must fail clearly before numbers can be rounded.

## Verification and package boundaries

- Use `node:test` and `node:assert/strict` for unit and fixture-driven tests with the built JS or explicit test transpilation. Use ESLint 10.16.0 with flat config, `@eslint/js` 10.0.1 and `typescript-eslint` 8.74.0 as dev tools. These versions install together with TS 5.9.3. Add test runner dependencies only if a concrete coverage or workflow gap requires them. [Node test runner](https://nodejs.org/api/test.html) · [ESLint](https://eslint.org/docs/latest/use/getting-started) · [typescript-eslint version support](https://typescript-eslint.io/users/dependency-versions/)
- Run public-only GitHub Actions on pull requests and default-branch pushes. Use an offline contract job with the existing pinned Python tools and a Node matrix covering the minimum and latest patch of each supported line. Check locked install, lint, types, deterministic generation and build, fixture tests, archive contents, and consumer imports against an actual tarball. The wider matrix costs runner time and exercises each advertised floor. Use `contents: read`, SHA-pinned approved actions, no persisted checkout credentials, and no secrets or release permissions. Confirm organization allowlisting and successful runs before requesting any required check changes. [GitHub Node CI](https://docs.github.com/en/actions/tutorials/build-and-test-code/nodejs) · [GitHub Actions security](https://docs.github.com/en/actions/reference/security/secure-use)
- Export only the supported root entry. Use a tight npm `files` allowlist for built JS and the declarations they require, plus the ordinary package metadata, README and license. Compare `npm pack --dry-run --json` and the real archive against the allowlist. Include synthetic ignored-file canaries at the repository root and in build output. Retain Git/npm exclusions and keep raw contract inputs, fixtures, scripts, plans, local instructions, local settings and private memory outside the archive. [npm package files](https://docs.npmjs.com/cli/v11/configuring-npm/package-json#files) · [npm pack](https://docs.npmjs.com/cli/v11/commands/npm-pack/)
- Keep local package testing independent of npm namespace ownership and retain `private: true` until an approved release change. Treat `@vat-engine/sdk` as the intended name pending registry resolution. Later publication requires a separate approved release workflow using trusted publishing on a supported hosted runner, provenance where supported, and publish permissions limited to that workflow. Gate A and Gate B retain independent release acceptance. [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/)

## Prototype evidence on the JS-01 pin

- The standalone verifier passed on the public archive of SDK `bbab7c4`. It checked 55 operations, 959 references, 22 cases, 33 exchanges and 14 supply-reference cases. Seven tooling tests passed. The OpenAPI remains pinned at `5158c7c19479d3e6db0e5617b249c7520177778dbabed8a8975c17319275f065`.
- Eleven prototype checks passed on Linux x64 with Node 22.13.0, 22.23.5, 24.0.0, 24.22.3, 26.0.0 and 26.13.1. They covered exact supply replay and signed bounds, both signs of overflow, unsafe-number rejection, wire type asymmetry, null/omission/false, the ECB double, cursor semantics and both attachment digests. The checks exercised synthetic values locally.
- Repeated type generation produced identical bytes on Node 22 and 26. The output covered all 55 method/path identities, including 13 without operation IDs. TypeScript checked a numeric supply revision as `bigint`, a quoted receipt revision as `string`, and the optional nullable ECB rate as `number | null | undefined`. The private native JSON typing compiled and preserved an unsafe magnitude on both Node lines.
- A temporary package packed with npm 11.20.0. Its dry run and actual pack reported identical allowlisted contents and excluded synthetic local files. An independent installation passed `import` and `require()` smoke tests on all six Node versions. The mixed-loader test shared export identity and blocked an internal deep import. TS 5.9.3 compiled both `.mts` and `.cts` consumers. ESLint ran on Node 22.13.0 and 26.13.1.

These experiments establish feasibility for the decision. JS-02 acceptance still requires the approved package skeleton, complete precision mapping, public-only CI and clean consumer tests of the SDK's own archive.
